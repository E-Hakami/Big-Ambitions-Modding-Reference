# Big Ambitions Modding Reference

An unofficial reference for understanding the internal C# code of **Big Ambitions** and its modding-related systems.

The repository contains decompiled C# source from specific game builds, along with automatically generated Markdown pages that make the code easier to navigate and understand.

> **This is an unofficial community reference and is not affiliated with the developers of Big Ambitions.**

---

# Repository Structure

The repository is organized by game build.


Each build contains the decompiled C# source produced from that version of the game.

Assembly folders represent the different compiled assemblies found in the game.

Files that were located directly at the root of the decompiled build are placed in ZZZ_RootFiles.

The reference is versioned by build so that code can be compared between different versions of the game.

# C# Source

The .cs files contain the decompiled C# source code.

They are the primary technical reference for the repository.

Depending on the source file, they may contain:

Classes
Interfaces
Enums
Methods
Fields
Other C# definitions

The source is generated by decompiling the game's compiled assemblies.

# Documentation

Each .cs file has a corresponding .md file.

For example:

**Builds/Build 3674/AI.Employees/Complaint.cs**
**Builds/Build 3674/AI.Employees/Complaint.md**

The Markdown file provides a simplified reference and navigation layer for the corresponding source file.

The documentation is automatically generated from the C# source.

How to Use the Reference

The Markdown documentation is primarily intended to make the large codebase easier to navigate.

Do not assume that the answer to a question is contained entirely within the first class or folder you find.

Big Ambitions systems frequently interact with classes located in different folders and assemblies.

When investigating how a system works, follow the relationships between the files.

**A useful workflow is:**

Identify the class or source file most relevant to the question.
Open its .md file.
Read the Uses section.
Follow relevant links to other classes.
Check Used By when you need to find what interacts with or calls the current class.
Open the corresponding .cs files when implementation details are needed.
Continue following Uses and Used By across folders and assemblies until the behavior is understood.
Use the original .cs source as the final technical reference.

The folder structure is useful for organization, but it should not be treated as a boundary for investigating a system.

For example:

AI.Employees
    ↓
Helpers
    ↓
Entities
    ↓
Messaging

A system may cross several folders before reaching the code responsible for the behavior being investigated.

AI-Assisted Investigation

**This repository is designed to be usable by both humans and AI assistants.**

The generated Markdown files act as a navigation layer over the decompiled C# source.

When answering a question about the game, an AI should:

Question
   ↓
Find relevant class
   ↓
Read its .md
   ↓
Check Uses
   ↓
Follow relevant links
   ↓
Inspect source
   ↓
Check Used By when necessary
   ↓

   ↓
Trace the complete behavior

# Uses

Uses answers:

What other known types does this source reference?

For example:

EmployeeManager

Uses:
- Employee
- EmployeeData
- EmployeeTask

Each entry links to the corresponding Markdown documentation.

This allows a user or AI to follow dependencies through the codebase.

# Used By

Used By answers:

What other source files reference this type?

For example:

EmployeeData

Used By:
- EmployeeManager
- BusinessManager

This is the reverse of Uses.

If:

A Uses B

then:

B Used By A

Used By is particularly useful when trying to determine how a class is used by the rest of the game.

Markdown File Structure

Generated Markdown files currently use the following structure:

# TypeName

**Type:** Class

## Main Reference

## Uses

## Used By

## Notes

The exact metadata may vary depending on the source file.

A source file may contain multiple declared types, or may not contain a traditional class at all.

Main Reference

Contains a link to the corresponding .cs source file.

Use this when the actual implementation needs to be inspected.

The .cs file is always considered the more complete technical reference.

Notes

The Notes section is reserved for information that cannot reliably be generated from the source automatically.

It can be used for:

Explanations of what a type appears to do
Important observations
Modding-related information
Known limitations
Examples
Research notes
Useful implementation details

Manual notes should be treated as supplementary information rather than a replacement for the original source.

# Builds

Each game build has its own directory.

For example:

**Builds/Build 3674/**

This allows the reference to preserve differences between game versions.

When working on a mod, use the reference corresponding to the version of Big Ambitions being targeted.

Future builds can be added without replacing the source from previous builds.

# Limitations

The dependency information is automatically generated and is not a complete C# semantic analysis.

For example, relationships may be missed or incorrectly detected in cases involving:

Duplicate type names
Namespaces with identical type names
Complex C# syntax
Types that cannot be identified from the source
References made indirectly through reflection
Runtime-generated behavior
External assemblies not included in the reference

For this reason:

The generated Markdown should be treated as a navigation aid, not as a replacement for reading the C# source.

Also, Github Blocks AIs from recursive searching the tree so you will need to give the AI a complete file directory URL to get it started on the navigation system using the .md files, or AI agents can simply use the suggested starting points.
